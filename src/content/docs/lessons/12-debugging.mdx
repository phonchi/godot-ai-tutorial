## 學習目標

1. 從錯誤訊息中讀出三件事：哪個檔案、哪一行、什麼東西是空的或錯的。
2. 使用 `print`、`push_warning`、`push_error`、`assert` 在不同情況下輸出資訊。
3. 使用除錯器的中斷點、逐行執行、變數檢視與「遠端」場景樹。
4. 使用「顯示碰撞形狀」與監視器（Monitors）排除物理與效能問題。
5. 把一個 bug 整理成「重現步驟、預期、實際、日誌」四段，交給 agent 分析。

## 核心概念

### 除錯的順序：先重現，再縮小，最後才修

不論是你自己或 agent，最浪費時間的方式是「看到錯誤就猜一個修法」。比較有效的順序是：

1. **重現**：找到能穩定觸發問題的操作步驟。
2. **縮小**：確認是哪個場景、哪個腳本、哪一行開始不對。
3. **假設與驗證**：提出一個原因，用 `print` 或中斷點證實，再修改。
4. **回歸檢查**：修好後，確認原本正常的功能沒有被弄壞。

### Godot 的錯誤從哪裡看

| 位置 | 內容 |
| --- | --- |
| 編輯器下方「輸出」 | `print` 的內容與一般訊息 |
| 「除錯器 → 錯誤」分頁 | 執行期的錯誤與警告，可以展開看呼叫堆疊 |
| 腳本編輯器底部 | 存檔時的語法錯誤，紅字標示行號 |
| 終端機 | 用 CLI 執行時的全部輸出 |
| 日誌檔 | `~/.local/share/godot/app_userdata/專案名稱/logs/godot.log` |

## 動手操作

### 步驟 1：讀懂三種常見錯誤

**空值存取**

```text
Invalid access to property or key 'text' on a base object of type 'Nil'.
```

意思是：你對一個 `null` 取 `text` 屬性。往前找這個變數從哪裡來，通常是 `$路徑` 寫錯、節點被改名、或在 `_ready` 之前就使用了 `@onready` 變數。（不同版本的訊息文字略有差異，例如舊版寫成 `Invalid get index 'text' (on base: 'Nil')`，意思相同。）

**呼叫不存在的函式**

```text
Invalid call. Nonexistent function 'can_take_damage' in base 'Area2D'.
```

意思是：你以為拿到的是玩家，其實拿到的是一個 `Area2D`。檢查群組成員或碰撞回呼中的 `body` 是誰。

**物理回呼中修改狀態**

```text
Can't change this state while flushing queries. Use call_deferred() or set_deferred() to change monitoring state instead.
```

訊息本身就給了解法：改用 `set_deferred` 或 `call_deferred`。

### 步驟 2：適當的輸出

```gdscript
# 示範概念：不同等級的輸出
func collect_item(star: Area2D) -> void:
	print("收集前：", score, " 本波：", wave_collected)     # 一般資訊
	if score > TARGET:
		push_warning("星星數超過目標：%d" % score)          # 黃色警告，會進入除錯器
	assert(state == State.PLAYING, "非進行中卻收到星星")  # 只在除錯版中檢查
```

- `print`：臨時觀察用，修好後記得移除，避免輸出被淹沒。
- `push_warning`、`push_error`：會出現在除錯器的錯誤分頁並附帶呼叫位置，適合「不該發生但不致命」的情況。
- `assert`：條件不成立時中斷執行；在匯出的發行版中會被忽略，所以不能用來處理正常流程。

### 步驟 3：中斷點與逐行執行

1. 在腳本編輯器中，點擊行號左側設定紅點（或按 `F9`）。
2. 按 F5 執行，觸發該行時遊戲會暫停，編輯器切到除錯器。
3. 在「堆疊框架」（Stack Frames）看是誰呼叫了這個函式；在「成員」與「區域變數」看當下的數值。
4. 用「逐步跳過」（Step Over，`F10`）一行行執行，用「逐步進入」（Step Into，`F11`）進入函式。
5. 按「繼續」恢復執行。

程式中也可以寫 `breakpoint` 關鍵字，效果和紅點相同。

### 步驟 4：遠端場景樹

遊戲執行時，場景面板上方會出現「遠端」（Remote）與「本機」（Local）切換。切到遠端可以看到**正在執行中**的場景樹：哪些星星還在、玩家的實際位置、某個節點的屬性目前是多少，甚至可以直接在檢查器修改來測試。

### 步驟 5：除錯選單

在編輯器上方的「除錯」選單勾選：

- **顯示碰撞形狀**：看到所有碰撞框與區域，最適合排查「為什麼碰不到」或「為什麼隔空被撞」。
- **顯示導航**：使用導航功能時才需要。

另外在除錯器的「監視器」分頁可以看到 FPS、節點數量、物件數量等。若節點數量一直增加不下降，代表有東西被產生卻沒被刪除。

### 步驟 6：用 CLI 收集日誌給 agent

```bash
godot --path . --headless --quit-after 600 2>&1 | tee /tmp/godot-run.log | tail -n 60
```

`tee` 會把完整輸出存到檔案，同時在畫面顯示最後 60 行。agent 可以讀 `/tmp/godot-run.log` 取得完整內容。但要記得：**很多 bug 只在特定操作後出現**，headless 執行不會有人按鍵，這類 bug 不會出現在日誌中。這時要由你操作重現，再把編輯器除錯器中的錯誤訊息複製給 agent。

### 步驟 7：用行為測試驗證規則

下載的完成品附有 `tests/behavior.gd`。它不開視窗，直接載入 `main.tscn`，用程式模擬「開始遊戲、衝刺、被追蹤者碰到、收完三個波次、重新開始」，逐條檢查規則：

```bash
godot --headless --path . --script res://tests/behavior.gd 2>&1 | tail -n 30
```

每一條規則印出一行 `ok` 或 `FAIL`，最後一行是 `BEHAVIOR CHECKS: PASS (0 failures)`。這補上了 headless 日誌的盲點：沒有人按鍵，測試會自己呼叫 `start_game()`、`collect_item()`、`damage_player()`，並等待真正的物理影格。請 agent 修改規則時，把「執行這個測試並貼出結果」寫進要求，比只看「沒有錯誤訊息」可靠得多。

測試也有界線：它驗證的是規則與數值，看不到顏色、動畫是否好看，也聽不到聲音。這些仍然要你在視窗中確認。

## 程式碼解說：一份好的 bug 描述

```text
重現步驟：
1. 執行主場景，按 Enter 開始
2. 打到第 3 波，收集到 9 顆星
3. 只剩 1 顆心時，同時碰到最後一顆星與追蹤者

預期：顯示 YOU WIN!
實際：顯示 GAME OVER，HUD 顯示星星 10 / 10、愛心全空

錯誤訊息：無
相關檔案：scripts/main.gd（collect_item、damage_player、end_game）
已嘗試：在兩個函式開頭 print state，兩者都印出 PLAYING（數值 1）
```

這份描述讓 agent 不必猜：它知道怎麼重現、哪裡不對、哪些可能性已經排除。對照第 10 章，你會發現這個 bug 的成因是同一影格內兩個事件都通過了 `is_playing()` 的檢查，問題不在單一函式，而在「誰先發生」的設計決策。

## 練習

1. 故意把 `start_wave()` 中的 `WAVES[index]` 改成 `WAVES[index + 1]`，執行行為測試，從錯誤訊息與 `FAIL` 行找回是哪一行出錯，再修正。
2. 在星星的碰撞回呼中直接寫 `monitoring = false`（不用 `set_deferred`），觀察錯誤訊息，再改回正確寫法。
3. 用監視器觀察：連續重開遊戲 10 次，節點數量是否穩定？
4. 為本頁「程式碼解說」中的 bug 決定一個規則（例如「同一影格先處理收集」），請 agent 依規則修正並提供驗證方式。

## 常見錯誤與限制

- **錯誤只在第一次出現**：Godot 對重複的錯誤可能只顯示一次或合併計數，看錯誤分頁的計數欄位。
- **修改後沒有生效**：忘記存檔，或執行的是另一個場景（F5 與 F6 的差別）。
- **`print` 太多看不到重點**：在 `_process` 中 `print` 每秒會輸出數十行，改成只在數值改變時輸出。
- **讓 agent 猜**：沒有錯誤訊息和重現步驟時，agent 只能猜，可能改掉正確的程式。先蒐集證據。
- **以為 headless 沒錯誤就沒 bug**：邏輯錯誤（例如勝負判斷順序）不會產生任何錯誤訊息。
