## 學習目標

1. 把一個模糊的遊戲需求，拆成數個「完成後可以被觀察到」的小任務。
2. 寫出有明確範圍的提示詞：要改哪些檔案、不能碰哪些東西、完成條件是什麼。
3. 用 `git diff` 審查 agent 的修改，知道哪些地方要特別注意。
4. 區分三個驗證層級：**能解析**、**能執行不報錯**、**畫面與手感正確**，並知道每一層由誰、用什麼工具確認。
5. 在結果不對時，能乾淨地退回上一個狀態重新來。

## 核心概念：一個循環，五個關卡

<LessonDiagram kind="workflow" />

和 agent 合作最常見的失敗不是「它寫不出來」，而是「它一次改太多，你看不出哪裡錯」。因此本課程的每一次修改都走同一個循環：

1. **拆解**：一次只要求一個可觀察的行為，例如「按 D 時角色往右移動」，而不是「做好玩家系統」。
2. **計畫**：先讓 agent 讀檔並說明打算怎麼改，你同意後才動手。
3. **有限修改**：在提示詞中寫明允許修改的檔案與禁止事項。
4. **看 diff**：修改後用 Git 檢查每一行變化。
5. **驗證**：依序跑三層驗證，全部通過才提交（commit）。

這個流程的前提是第 5 章已經把專案放進 Git，並寫好 `AGENTS.md` 或 `CLAUDE.md`。

## 動手操作

### 步驟 1：把需求拆成可觀察的任務

以 2D 遊戲的「玩家能移動」為例，可以拆成：

| 任務 | 完成後你能觀察到什麼 |
| --- | --- |
| A. 建立輸入動作 | 專案設定的輸入對應中出現 `move_left` 等動作，且綁定了 WASD 與方向鍵 |
| B. 玩家場景 | 有一個可以單獨執行的玩家場景，畫面中看得到角色形狀 |
| C. 移動腳本 | 按住方向鍵角色會移動，放開就停 |
| D. 碰牆 | 角色撞到邊界牆會停下，不會穿過去 |

每一列都是一次獨立的對話或一次獨立的提交。好的任務描述包含「要做什麼」和「怎樣算完成」，而不是「怎麼實作」——實作細節讓 agent 提案，你來審核。

### 步驟 2：先要計畫，不要直接改

兩個 CLI 都有適合「只讀不寫」的工作方式：

- **Claude Code**：可以切換到計畫模式（Plan mode，常見操作是在輸入框按 `Shift+Tab` 循環切換模式），此時它只會讀檔與提出計畫，不會修改檔案。
- **Codex CLI**：可以用 `/permissions` 或 `/approvals` 指令（名稱依版本而異，請以 `/help` 列出的指令為準）切換到唯讀模式；或者直接在提示詞中寫「只讀取、不要修改，先給我計畫」。

不論哪一種，提示詞中明確寫「先不要修改」都是最可靠的保險。

### 步驟 3：寫出有邊界的提示詞

一個有邊界的提示詞包含五個部分：

```text
背景：這是 Godot 4.x GDScript 專案，主場景是 main.tscn。
任務：讓玩家角色在按下 WASD 或方向鍵時移動，速度可在檢查器調整。
範圍：只能修改 player.gd；若需要新增輸入動作，先列出來讓我在編輯器中手動新增。
禁止：不要修改 .tscn 檔、不要新增外掛、不要改專案設定以外的檔案。
完成條件：執行 godot --path . --headless --quit-after 120 沒有錯誤，並說明我該如何手動測試。
```

「禁止修改 `.tscn`」不是絕對規則，而是新手階段的好習慣：場景檔雖然是文字格式，但包含資源編號與 UID，手改容易出錯，在編輯器中操作更安全。等你熟悉格式後可以放寬。

### 步驟 4：審查 diff

agent 說「完成了」之後，先不要急著執行遊戲，在另一個終端機中：

```bash
git status            # 哪些檔案被改了？有沒有超出範圍的檔案？
git diff --stat       # 每個檔案改了幾行？
git diff              # 逐行檢查
```

審查時特別注意：

- 被修改的檔案是否都在你允許的範圍內。
- 有沒有被刪掉的既有程式碼，尤其是訊號連接與 `@export` 變數。
- 有沒有出現你沒要求的新功能、新檔案或新相依套件。
- `project.godot` 是否被改動。它會影響整個專案，必須逐行確認。

### 步驟 5：三層驗證

| 層級 | 驗證什麼 | 方法 | 誰可以做 |
| --- | --- | --- | --- |
| 1. 能解析 | 腳本沒有語法錯誤 | `godot --path . --headless --quit` | agent |
| 2. 能執行 | 跑一段時間沒有執行期錯誤 | `godot --path . --headless --quit-after 300`，並讀日誌 | agent |
| 3. 畫面與手感 | 角色看得到、方向正確、速度合理 | 開視窗實際玩 | 你；或有畫面工具的 agent |

第 1、2 層只能證明「沒有報錯」，不能證明「行為正確」。例如角色往反方向移動、或被畫在畫面外，headless 執行都不會報任何錯。

第 3 層有兩種做法：

- **你自己玩**：最直接，也最能判斷手感。
- **錄製影格給 agent 看**：Godot 的 Movie Maker 模式可以把執行畫面輸出成圖片序列，例如 `godot --path . --write-movie /tmp/frames/frame.png --quit-after 120`。這需要真的建立視窗繪圖（不能加 `--headless`），而 agent 是否能讀取圖片取決於你使用的工具與授權。即使 agent 看了圖片，也只能檢查靜態畫面，不能替代實際操作手感。

### 步驟 6：提交或退回

驗證通過就提交：

```bash
git add -A
git commit -m "玩家可用 WASD 與方向鍵移動"
```

驗證失敗、而且 agent 修了兩三次仍越改越亂時，不要繼續疊加修改。直接退回上一次提交，重新拆小任務：

```bash
git restore .          # 丟棄所有尚未提交的修改（無法復原，先確認）
git clean -n           # 先預覽會被刪除的新檔案
git clean -fd          # 確認後才真正刪除
```

## 程式碼解說：讓 agent 驗證時一定會結束

agent 執行遊戲時若沒有結束條件，會一直等待到逾時。請在規則檔或提示詞中固定使用：

```bash
godot --path . --headless --quit-after 300 2>&1 | tail -n 50
```

- `2>&1`：把錯誤輸出合併進一般輸出，避免只看到一半的訊息。
- `tail -n 50`：只保留最後 50 行，避免大量輸出塞滿 agent 的對話內容。若需要完整內容，請 agent 改讀日誌檔。

## 自我檢查

- [ ] 我的每個任務描述都有「完成後能觀察到什麼」。
- [ ] 我在 agent 修改前就知道它預計會碰哪些檔案。
- [ ] 我在提交前看過 `git diff`，且所有修改都在範圍內。

## 練習

1. 把「做出 2D 收集遊戲的計分 UI」拆成至少四個可觀察的小任務，並為每個任務寫出完成條件。
2. 請 agent 用計畫模式（或唯讀模式）分析一個小修改，然後故意拒絕它的第一個計畫、要求更小的範圍，觀察它如何調整。
3. 故意讓 agent 引入一個錯誤（例如要求它把某個節點路徑改錯），然後只靠 headless 日誌找出問題，體會第 2 層驗證能抓到什麼。

## 常見錯誤與限制

- **一次要太多**：一個提示詞包含五個功能時，出錯很難定位。寧可多開幾次小對話。
- **只看 agent 的總結**：agent 的總結可能遺漏它順手改的地方，`git diff` 才是事實。
- **把 headless 通過當成完成**：沒有錯誤訊息不代表遊戲行為正確，畫面與手感一定要人工確認。
- **讓 agent 長時間自動核准所有操作**：方便但風險高。本課程建議維持需要確認的權限模式，只對讀檔、執行 Godot、`git diff` 這類低風險指令放寬。
- **上下文太長**：同一個對話做了很多事之後，agent 可能混淆舊的計畫。完成一個任務並提交後，開新對話繼續。
